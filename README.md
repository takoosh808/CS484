
# THEIA — Indoor Navigation for Blind and Visually Impaired Users

**Cpt S 484 | Washington State University | Fall 2026**

**Team:** Ubuntu Bros

**Project Status:** Phase I — Requirements Engineering and Mock-up Prototype

## Overview

**THEIA** is a proposed smartphone application designed to help blind and visually impaired (BVI) individuals navigate indoor environments safely and independently.

The application aims to provide accessible navigation assistance through voice instructions, audio feedback, vibration cues, and an interface designed for users with limited or no vision.

This repository contains the requirements engineering documentation, project planning materials, usage scenarios, and prototype developed as part of the Cpt S 484 Software Requirements course at Washington State University.

> **Note:** Phase I focuses on requirements analysis, documentation, and developing a mock-up prototype. A fully functioning navigation application is outside the scope of this phase.

## Project Objectives

The primary goal of THEIA is to explore how accessible technology can improve indoor navigation for blind and visually impaired individuals.

Our project objectives include:

1. Identify challenges faced by BVI individuals when navigating indoor environments.
2. Analyze and document software requirements using a structured requirements engineering process.
3. Develop functional and non-functional requirements for the proposed application.
4. Design an accessible user interface that prioritizes non-visual interactions.
5. Create realistic usage scenarios demonstrating how THEIA could assist users.
6. Develop a mock-up prototype illustrating the application's intended functionality.
7. Document design decisions, requirements traceability, and project progress.

## Proposed Features

### Indoor Navigation

- Allow users to select and confirm indoor destinations.
- Provide spoken turn-by-turn navigation instructions.
- Allow users to repeat, pause, or cancel instructions.
- Communicate navigation status through audio feedback.

### Obstacle Awareness

- Demonstrate warnings for obstacles or blocked pathways.
- Allow users to pause navigation when a potential obstacle is encountered.
- Present alternative route options when available.

### Voice and Audio Accessibility

- Voice-based navigation instructions.
- Adjustable instruction volume and frequency.
- Spoken confirmation of user actions.
- Compatibility with screen readers as a design goal.

### Assistance Requests

- Allow users to request assistance from a selected support contact.
- Provide clear feedback when the user's location cannot be determined.
- Pause navigation when accurate directions cannot be provided.

### Accessible User Interface

- Large, high-contrast text and buttons.
- Minimal reliance on visual interaction.
- Audio and vibration feedback.
- Simple navigation controls.

**Important:** These features represent proposed functionality explored through the Phase I prototype. They are not currently implemented as a working navigation system.

## Use Case Scenarios

The project explores four primary scenarios using AS-IS and TO-BE analysis.

### Scenario 1: Navigating to a Classroom

**AS-IS:** A visually impaired student attempts to reach a classroom but misses a turn and encounters a wall.

**TO-BE:** THEIA confirms the selected classroom destination and provides spoken navigation instructions to guide the student.

### Scenario 2: Encountering a Blocked Hallway

**AS-IS:** A user encounters an unexpected obstruction while navigating a building.

**TO-BE:** THEIA demonstrates how an obstacle warning could be communicated and allows the user to stop or select another route.

### Scenario 3: Requesting Assistance

**AS-IS:** A visitor becomes lost inside a building and struggles to describe their location.

**TO-BE:** THEIA recognizes uncertain location information in the simulated scenario, pauses navigation, and demonstrates requesting assistance from a selected contact.

### Scenario 4: Adjusting Navigation Settings

**AS-IS:** A user struggles with navigation instructions that are too quiet or delivered too frequently.

**TO-BE:** THEIA provides accessible settings through spoken prompts, allowing the user to preview and confirm adjustments.

## Development Methodology

THEIA follows an iterative requirements engineering process.

### 1. Planning

- Review the preliminary project definition.
- Establish project goals and scope.
- Assign team responsibilities.
- Develop a project management plan.

### 2. Requirements Analysis

- Identify incomplete, ambiguous, inconsistent, redundant, or unsound requirements.
- Propose resolutions for identified issues.
- Document reasoning behind design decisions.

### 3. Requirements Specification

- Define project problems and goals.
- Identify functional and non-functional requirements.
- Develop requirement specifications.
- Create traceability relationships between problems, goals, objectives, and requirements.

### 4. Prototype Development

- Create interface mock-ups.
- Demonstrate navigation interactions.
- Incorporate accessibility considerations.
- Document expected user interactions.

### 5. Validation and Review

- Develop AS-IS and TO-BE scenarios.
- Review documentation for consistency.
- Evaluate the prototype against documented requirements.
- Prepare the final presentation and deliverables.

## Accessibility Considerations

Accessibility is a central objective of THEIA.

The proposed interface prioritizes:

- Non-visual interaction.
- Clear and understandable spoken instructions.
- Haptic feedback.
- Adjustable accessibility settings.
- High-contrast visual elements for users with low vision.
- Feedback when navigation information is unavailable or uncertain.

The Phase I prototype is intended to demonstrate accessible interactions but has not been validated as a working assistive navigation system.

## Safety and Limitations

THEIA is currently an academic prototype.

Phase I does not include:

- Real-time indoor positioning.
- Functional obstacle detection.
- Operational emergency communication.
- Real-world navigation testing.
- Production-ready navigation capabilities.

The mock-up demonstrates how these interactions could work in a future implementation.

The application should not be relied upon for actual navigation or safety assistance in its current state.
